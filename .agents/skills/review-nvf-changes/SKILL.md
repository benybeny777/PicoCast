# 変更をレビューする

利用者が「読み取り専用」「編集禁止」と明示していない限り、レビューは修正・テストまでの依頼として扱う。指摘を並べて終わりにしない。

## 対象を決める

1. 依頼から対象を1つに決める。コミット範囲・ブランチ → その範囲。「直近の変更」→ 直近10コミット。未コミット変更 → 作業ツリー。
2. `git log --oneline <範囲>` と `git diff --stat <範囲>` で規模を掴む。生成物・画像・DB は差分を読まず参照だけ確認する。
3. 既存の未コミット変更は利用者または別エージェントの作業として扱い、巻き戻さない。

## 読む

差分を上から読むのではなく、変更された関数ごとに次を行う。

1. **主張と実装を照合する。** コミットメッセージや CHANGELOG が言う修正が全経路で成り立つか。直した経路の隣に同じ欠陥が残っていないか。
2. **呼び出し元と全経路を追う。** 正常・失敗・キャンセル・タイムアウト・チャンネル切替直後・設定変更直後を `rg` で呼び出し元を列挙して確かめる。Web プロセスと `workers.runner` の両方から呼ばれるものは両方を見る。
3. **共通観点を必ず見る。**
   - 利用者が許可していないフォールバックが無いか（`AGENTS.md`）。`# フォールバック許可:` は根拠（会話・文書の利用者決定）が辿れるかで判定し、コメントの有無だけで判定しない。
   - コピペで作った類似コードが無いか。1件見つけたら特徴的な文字列で全体を `rg` し、同型を列挙して共通化する。
   - 読めない・壊れた入力を空で続け、その空を DB へ保存していないか。
   - 失敗を `continue`・早期 `return`・`except Exception: pass`・ログだけで済ませていないか。「解釈できない」が「指定なし」と同じ値に落ちていないか。
   - 独立した後処理を1つの `try` にまとめ、前段の失敗で後段が飛ばないか。
   - ファイル・DB接続・subprocess・画像/動画オブジェクトが全経路で明示的に解放されるか（GC任せ禁止）。
   - active profile 以外の `output_root` やテンプレートを参照していないか（`safe_output_path()` / `find_history_dir()` を通るか）。
   - 秘密値がレスポンス・ログ・例外・job ログ・診断ZIPへ出ないか。スタックトレースが利用者向け表示へ出ないか。
   - 長時間処理が HTTP リクエスト内で待っていないか（`job_manager` でジョブ化されているか）。
   - 追加したテストが、退行を仕込むと本当に落ちるか。
   - 変える行の導入理由を `git log -L <開始>,<終了>:<ファイル>` かコメントで確かめたか。
4. **文書と照合する。** `SPEC.md` と食い違うときは文書を正としてコードを疑う。文書が誤っていると判断したら該当箇所と訂正案を報告する。

## 判定する

- 実害の経路（どの入力・操作・状態で、利用者に何が起きるか）を辿れたものだけを指摘にする。辿れない懸念は実際に確かめ、問題が無ければ「確認して問題なし」に記録する。
- 重要度:
  - P0: データ消失、起動不能、秘密値の露出、意図しない YouTube 投稿・公開、販売物への開発用表示の混入。
  - P1: 機能が黙って動かない、誤った内容を生成・表示する、プロセスやリソースが残る、費用（Gemini / ChatGPT API）を無駄に使う。
  - P2: 一部条件での表示崩れ・競合、検査の穴、文書のずれ、dead code。
  - P3: 命名・表記・軽微な一貫性。
- 意図的な設計を不具合と取り違えない。待ち時間や閾値などは導入理由を確かめてから判断する。

## 直す

1. P0〜P2 は同じ作業内で直す。見つけた同型も直す。方針判断が要るものも妥当な既定を選び、採否と理由を記録する。
2. 直した不具合ごとに回帰テストを足すか、既存テストで固定済みであることを示す。実装の言い換えだけのテストは足さない。
3. 同じ型が3回以上再発しているなら、個別テストではなく共通層への集約で構造的に防ぐ。
4. 恒久ルールに値する再発防止策は `AGENTS.md` へ同じ作業で追記する。

## 記録する

コミットメッセージ（PR を作る場合は PR 本文）に次の形で書く。

```markdown
## 対象
<範囲・コミット>。読んだ観点: 共通観点、…

## 指摘と対応
| # | 優先 | 指摘 | 判定 | 対応・根拠 |
|---|---|---|---|---|

## 確認して問題なし
- <観点>: <根拠>

## 検証
- 実行: <コマンドと結果>
- 未確認: <実機・外部サービスが要るもの>
```

## 検証する

1. `./.venv/Scripts/python.exe -m pytest -q`（変更範囲が狭ければ関係テストから）。
2. JS を変えたら `node --test tests/*.mjs` と `node --check <変更したJS>`。
3. 画面を変えたら Web UI を起動して該当画面を目視する。確認できなかった範囲は未確認として書く。
