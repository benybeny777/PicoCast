# yukkurijidouの変更をレビューする

`AGENTS.md` のとおり、利用者が「読み取り専用」「編集禁止」と明示していない限り、レビューは修正・テストまでの依頼として扱う。指摘を並べて終わりにしない。

## 対象を決める

1. 依頼から対象を1つに決める。
   - PR番号 → そのPRの差分（`origin/<base>...<head>`）。
   - ブランチ・コミット範囲 → その範囲。
   - 「直近の変更」 → 前回レビュー以降の `main`。`git log --format='%h %s' origin/main | grep -m1 'レビュー'` で起点を探し、見つからなければ直近10コミット。
   - 未コミット変更 → `origin/main` との差分と作業ツリー。
2. `git fetch origin main` してから `git log --oneline <範囲>` と `git diff --stat <範囲>` で規模を掴む。画像・PSD・音声・生成物は差分を読まず、参照と寸法だけを確認する。
3. 既に未コミット変更がある場合は利用者または別エージェントの作業として扱い、巻き戻さない。
4. レビューは作業中のエージェント自身で完結させる。CodexとClaudeは互いを起動しない（`AGENTS.md`）。

## 準備する

1. `AGENTS.md` を読む。変更対象に応じて `SPEC.md`・`README.md`・`MANUAL.md`・`BUILD.md` の該当節だけを読む。
2. 対象のPR本文またはコミットメッセージを読み、変更が主張する目的・不変条件・未確認事項を書き出す。

## 読む

差分を上から順に読むのではなく、変更された関数ごとに次を行う。

1. **主張と実装を照合する。** PR本文・コミットメッセージが言う修正が、全経路で本当に成り立つか。「直した」経路の隣に同じ欠陥が残っていないか。
2. **呼び出し元と全経路を追う。** 正常・失敗・中断・タイムアウト・再実行・設定変更直後・profile切替直後を、`rg` で呼び出し元を列挙して確かめる。Web プロセスと `workers.runner` の両方から呼ばれる関数は両経路を見る。
3. **共通観点を必ず見る。**
   - 利用者が指示していないフォールバックが無いか（下の「フォールバックとコピペを当てはめる」）。
   - コピペで作った類似コードが無いか（同上）。
   - 読めない・壊れた入力を空で続け、その空を保存へ流していないか。
   - 失敗を `continue`・早期 `return`・`except: pass`・ログだけで済ませていないか。失敗箇所で `_logger.error(..., exc_info=True)` を残しているか。「解釈できない」が「指定なし」と同じ値へ落ちていないか。
   - ユーザー向けログ・画面・APIレスポンスへスタックトレースや秘密値を出していないか。停止系エラーが `ERROR_CATALOG` の `E-...` コード経由か。
   - 独立した後処理を1つの `try` にまとめ、前段の失敗で後段が飛ばないか。
   - 確保したファイル・subprocess・接続・画像/動画オブジェクトが全経路で解放されるか。
   - active profile の分離（`require_active_profile()`、`safe_output_path()`、`find_history_dir()`、profile_id 単位の秘密値・BGM・テンプレート）を破っていないか。特定チャンネル名のハードコードや別 profile へのフォールバックが無いか。
   - 設定値のハードコード、`.env` / `os.environ` を正本にした新規設定、`config/config.py` 定数のコメント漏れが無いか。
   - 台本本文を `script.txt` から読んでいないか（正本は `metadata.db` の `videos.script_content`）。
   - 追加したテストが、退行を仕込むと本当に落ちるか。
   - 変える行の導入理由を `git log -L <開始>,<終了>:<ファイル>` かコメント・PR本文で確かめたか。
4. **同型を全体から探す。** 1件見つけたら、同じ書き方・同じ責務を `rg` で全体検索する。
5. **文書と照合する。** 担当文書と食い違うときは文書を正としてコードを疑う。文書自体が誤っていると判断したら、該当箇所と推奨する訂正を利用者へ報告する。

## フォールバックとコピペを当てはめる

規則の正本は `AGENTS.md`。ここではレビューでの当て方だけを書く。差分だけでなく、触れた関数の既存コードにも当てはめる。

- **フォールバック**:
  - 失敗・欠損・未対応の分岐を `rg` で列挙し、別手段への切替・既定値への降格・読み替え・飛ばしになっていないかを見る。`# フォールバック許可:` も手掛かりにする。
  - 許可には利用者の明示許可が要る。根拠を辿れたら指摘表の「対応・根拠」へ書き、辿れなければ撤去を指摘する。コメントの有無だけで判定しない。
  - 重要度: 利用者に見えない形で別の結果を見せる・保存する・アップロードするものはP1。表示だけが既定値へ落ちるものはP2。
- **コピペ**:
  - 1件見つけたら、特徴的な文字列・呼び出しの並び・定数で全体を `rg` し、同型を表にして列挙する。
  - 写しの片方だけに修正が入り、もう片方に既知の不具合が残るものはP1。保守だけを難しくする重複はP2。
  - 共通化しないと判断したものは、理由を「確認して問題なし」へ書く。

## 判定する

- 実害の経路（どの入力・操作・状態で、利用者に何が起きるか）を具体的に辿れたものだけを指摘にする。辿れない懸念は実際に確かめ、問題が無ければ「確認して問題なし」に記録する。
- 重要度:
  - P0: データ消失、起動不能、秘密値の露出、別チャンネルへの誤アップロード・誤操作、販売物への開発用データの混入。
  - P1: 機能が黙って動かない、誤った内容を見せる・アップロードする、プロセスやリソースが残る、特定OSで壊れる、課金APIを無駄に呼ぶ。
  - P2: 一部条件での表示崩れ・競合、テストの穴、文書のずれ、dead code。
  - P3: 命名・表記・軽微な一貫性。
- 意図的な設計を不具合と取り違えない。待ち時間、並列数、閾値のように変えると別の体験が壊れる値は、導入理由を確かめてから判断する。

## 直す

1. 変更規模が大きい・影響範囲が広い場合は `origin/main` から目的別ブランチを作る（`AGENTS.md`）。他人の未マージPRなら変更を提案して作者の判断を待つ。
2. P0〜P2は同じ作業内で直す。見つけた同型も直す。方針判断が要るものも妥当な既定を選び、採否・理由・代替案を記録へ書く。
3. 直した不具合ごとに `tests/` へ回帰テストを足すか、既存テストで固定済みであることを示す。追加したテストは修正前のコード（または退行を仕込んだ状態）で落ちることを確かめる。実装の言い換えだけのテストは足さない。
4. 外部API（Gemini・OpenAI・YouTube 等）が絡むテストはモックにする。費用が発生するAPIを確認のために実行しない（`AGENTS.md`）。
5. 恒久ルールに値する再発防止策は `AGENTS.md` へ同じ作業で追記する。

## 検証する

変更が出揃ってから、影響に合う段だけを最小回数で実行する。

1. 変更したモジュールに対応するテスト: `python -m pytest tests/<対象>.py -q`
2. Web UI・API を変えたら `python -m pytest tests/test_web.py -q`
3. 最終確認は `python tools/verify.py`（pytest・Node.js回帰テスト・共通JS構文・差分検査）。既に同じ段を実行済みなら重複実行しない。画面を変更したら実ブラウザで表示と対象操作も確認する。
4. 実機（VOICEVOX・SD WebUI・YouTube・Windows exe）が要る確認は、この環境で実行できなければ未確認として分けて書く。

## 記録する

PR本文（PRが無い場合は作業報告）をレビュー記録の正本にし、別のMarkdown台帳へ複写しない。次の形で書く。

```markdown
## 対象
<範囲・コミット・PR番号>。読んだ観点: 共通観点、…

## 指摘と対応
| # | 優先 | 指摘 | 判定 | 対応・根拠 |
|---|---|---|---|---|
| 1 | P1 | <どの条件で利用者に何が起きるか> | 対応済み | <修正内容、回帰テスト名> |

## 見送り・保留
| # | 内容 | 判定 | 理由・着手条件 |

## 確認して問題なし（再走査を省くため）
- <観点>: <根拠>

## 検証
- 実行: <コマンドと結果>
- 未確認: <実機・GUI・外部サービスが要るもの>
```

その後は `AGENTS.md` のとおり関連差分をコミットしてプッシュする。
